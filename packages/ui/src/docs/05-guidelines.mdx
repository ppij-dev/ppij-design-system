# Guidelines

Carried from the PPIJ guideline book (ppij-identity-sso, design/1.0.6) and
adapted to the library. The full batch by batch carry lands in Batch 11 of the
foundation change; the binding rules already live in the spec.

## Rules that never bend

1. **Tokens only.** Components use token names, never raw hex values or one
   off pixel literals.
2. **Tabler icons only.** No text glyphs as icons, no second icon family.
3. **No story, no component.** Every component renders in a story with its
   applicable states: default, loading, empty, error, disabled, long text.
4. **Presentation only.** No data logic, no API clients, no business logic,
   no secrets in this repo. Application strings arrive as props.
5. **Consume, never copy.** Applications import from the pinned package.
6. **Language switch** is a quiet text action or a labelled menu, never
   isolated boxed EN or ID codes.
7. **States are designed, not improvised.** Loading shows a layout matched
   skeleton, errors offer a retry, empty states say what is missing and what
   to do next.

## Surfaces

- **Public**: brand first, generous spacing, one clear action per section
- **Portal**: quiet and task focused, the member finishes a flow without
  decoration competing for attention
- **Admin**: dense but calm, one table pattern, one drawer pattern, badges
  carry live counts only and show nothing at zero

## Which surface when

Pick the smallest surface that fits the task. The same job always uses the
same surface, on every page.

| Job | Surface |
| --- | --- |
| Decide one thing, or acknowledge a notice | Dialog |
| Confirm a destructive action | AlertDialog, action named in full |
| Fill a multi-field form, or review before saving | Drawer (desktop) or bottom sheet (phone) |
| Report a finished action | Toast |
| Show a notice that must still be visible later | Inline Alert |

<div className="ppij-guideline-grid">
  <div className="ppij-guideline-card">
    <span className="ppij-guideline-label" data-kind="do">Do</span>
    <p>
      **Toast: one short sentence, one at a time.** "Perubahan tersimpan."
      A success with an undo action is the model case: the action finished,
      the toast reports it, and then it leaves.
    </p>
  </div>
  <div className="ppij-guideline-card">
    <span className="ppij-guideline-label" data-kind="dont">Do not</span>
    <p>
      Never put an error that needs action, form validation, or critical
      information in a toast alone. Validation errors belong at the field;
      errors that block work belong in an Alert or a Dialog. Never stack
      several toasts for one action.
    </p>
  </div>
</div>

## Editing: read-first panels, one drawer

Every editable surface uses the same pattern, so a person learns it once
and an agent builds it once.

- Data opens as text in an **EditablePanel**: title, one behaviour line,
  committed values, one Edit action. The panel itself is never a form.
- Edit opens the **AdminDrawer**: a right drawer from 900 px wide, a
  bottom sheet below that. One editor is open at a time.
- The drawer footer is Batal plus the submit. Direct saves read
  **Simpan perubahan**; changes that need review read **Ajukan
  perubahan**.
- The saving state lives inside the submit button. After the drawer
  closes, a status line confirms the result.
- A reviewed change leaves its proposal inside the panel with a
  **Menunggu** badge. Current values stay in effect until approval;
  nothing is overwritten early.

  <div className="ppij-guideline-card">
    <span className="ppij-guideline-label" data-kind="do">Do</span>
    <p>
      **Panel reads, drawer edits.** The profile is the model: each panel
      shows its values as text, and Edit opens that panel's form in the
      drawer (right on desktop, bottom sheet on the phone).
    </p>
  </div>
  <div className="ppij-guideline-card">
    <span className="ppij-guideline-label" data-kind="dont">Do not</span>
    <p>
      Never swap a reading view for an inline form, and never open a page
      as one long form. If a surface is worth reading, it opens as
      reading; editing is a separate, deliberate step.
    </p>

</div>

## Button action intents

A button states its intent by color. The words on the button say what
happens; the variant says how much care it needs.

| Intent | Variant | Use for |
| --- | --- | --- |
| Normal | default | The standard action on a surface: save, submit, continue |
| Confirm | success | Approving or completing: Setujui, Konfirmasi, Selesaikan |
| Alert | warning | Consequential but reversible: Arsipkan, Nonaktifkan |
| Danger | destructive | Destructive: Hapus. Always behind an AlertDialog |

One surface carries one primary intent. Danger is never the primary
button on a surface; it sits apart and confirms first.
